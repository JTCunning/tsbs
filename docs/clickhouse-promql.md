# TSBS Supplemental Guide: ClickHouse PromQL

[ClickHouse](https://github.com/ClickHouse/ClickHouse) exposes a native
Prometheus HTTP API that answers PromQL queries over data stored in a
TimeSeries table. The `clickhouse-promql` format benchmarks that API. It is
separate from the `clickhouse` format, which benchmarks SQL queries over the
ClickHouse native protocol.

The `clickhouse-promql` format covers query generation only. There is no
dedicated loader or query runner binary:

- Data is loaded through the Prometheus remote-write protocol. The format
  reuses the `prometheus` target, so `tsbs_generate_data` and `tsbs_load`
  produce and send Prometheus remote-write data.
- Generated queries are standard Prometheus HTTP API requests
  (`GET /api/v1/query_range`), so any HTTP-based PromQL runner works. The
  examples below use `tsbs_run_queries_victoriametrics`, which sends each
  query to a configurable base URL.

**This should be read *after* the main README.**

## Server setup

The ClickHouse server needs a TimeSeries table and Prometheus protocol
handlers for remote write and the HTTP query API. Example server
configuration:

```xml
<clickhouse>
    <prometheus>
        <port>9092</port>
        <handlers>
            <write_rule>
                <url>/api/v1/write</url>
                <handler>
                    <type>write</type>
                    <table>default.prometheus</table>
                </handler>
            </write_rule>
            <query_rule>
                <url>/api/v1/query</url>
                <handler>
                    <type>query</type>
                    <table>default.prometheus</table>
                </handler>
            </query_rule>
            <query_range_rule>
                <url>/api/v1/query_range</url>
                <handler>
                    <type>query</type>
                    <table>default.prometheus</table>
                </handler>
            </query_range_rule>
        </handlers>
    </prometheus>
</clickhouse>
```

The TimeSeries table engine is experimental; enable
`allow_experimental_time_series_table` in the user profile and create the
table before loading:

```sql
CREATE TABLE default.prometheus ENGINE = TimeSeries;
```

Consult the ClickHouse documentation for the current state of these settings
in your server version.

## Data format and loading

Data generated by `tsbs_generate_data --format=clickhouse-promql` is
serialized in the Prometheus remote-write format, identical to
`--format=prometheus`. Each field of a reading becomes a separate time
series whose metric name is the field key without a measurement prefix
(e.g. `usage_user`, not `cpu_usage_user`).

```text
$ tsbs_generate_data --use-case="cpu-only" --seed=123 --scale=100 \
    --timestamp-start="2016-01-01T00:00:00Z" \
    --timestamp-end="2016-01-02T00:00:00Z" \
    --log-interval="10s" --format="clickhouse-promql" \
    --file=/tmp/clickhouse-promql-data
```

Load it with `tsbs_load`. Generate the example config, then set the file
location and the adapter write URL to the ClickHouse remote-write endpoint
configured above:

```text
$ tsbs_load config --target=clickhouse-promql --data-source=FILE
$ # edit config.yaml:
$ #   data-source.file.location: /tmp/clickhouse-promql-data
$ #   loader.db-specific.adapter-write-url: http://localhost:9092/api/v1/write
$ tsbs_load load clickhouse-promql --config=./config.yaml
```

## Generating queries

Query generation works the same way as for other formats:

```text
$ tsbs_generate_queries --use-case="cpu-only" --seed=123 --scale=100 \
    --timestamp-start="2016-01-01T00:00:00Z" \
    --timestamp-end="2016-01-02T00:00:01Z" \
    --queries=1000 --query-type="cpu-max-all-1" --format="clickhouse-promql" \
    | gzip > /tmp/clickhouse-promql-cpu-max-all-1-queries.gz
```

PromQL cannot express all the devops query types, so the generator supports
the same subset as the VictoriaMetrics generator:

- `single-groupby-*` (all variants)
- `cpu-max-all-*` (all variants)
- `double-groupby-*` (all variants)

Not supported: `groupby-orderby-limit`, `lastpoint`, `high-cpu-1`,
`high-cpu-all`. The `iot` use case is not implemented.

The ClickHouse PromQL engine does not implement the `*_over_time` window
functions yet, so the generated queries aggregate the instant vector at each
step (`max(selector) by (__name__)`) instead of the
`max(max_over_time(selector[step]))` form the VictoriaMetrics generator
uses. At each step the engine picks the latest sample per series within the
lookback window rather than the maximum or average over the full step, so
results are not numerically comparable with other databases until
`*_over_time` support lands and the generator is updated.

## Running queries

The generated queries are relative HTTP requests
(`/api/v1/query_range?query=...&start=...&end=...&step=...`), executed by
prepending a base URL. Use `tsbs_run_queries_victoriametrics` with `--urls`
pointing at the ClickHouse Prometheus protocols port:

```text
$ cat /tmp/clickhouse-promql-cpu-max-all-1-queries.gz | gunzip | \
    tsbs_run_queries_victoriametrics --workers=8 \
    --urls=http://localhost:9092
```

If the handlers in the server configuration do not set a fixed `table`, the
target table can be passed per request through the `database` and `table`
query parameters.
